# App Event Tracker Simulator

An Android app that reports events through a small SDK, deduplicates them, queues them in Room and simulates unreliable ingestion with random delays, random failures and retries until every event is processed.

## Architecture

```
:app
  ↓
Analytics.reportEvents(json)
  ↓
:sdk
  ↓
Parse → Enrich → Deduplicate
  ↓
Room Event Queue
  ↓
Event Processing / Retry
  ↓
Processed Events
  ↓
:app UI
```

### Module Responsibilities

#### `:app`

Consumer/demo application.

Contains:

- Mock Data screen
- Event Queue screen
- Statistics screen
- Bottom navigation
- UI state and presentation
- Calls the SDK through `Analytics.reportEvents()`

#### `:sdk`

Core event-tracking SDK.

Contains:

- Public `Analytics` API (report events, observe queue and statistics, manual retry)
- JSON parsing
- Event models
- Session management
- Installation ID management
- Deduplication
- Room database
- Event queue
- Event processing
- Retry mechanism
- Processing status management

**The SDK contains no UI.**

## Architectural Decisions

### 1. Two-module architecture

We chose `:app` and `:sdk` instead of putting everything inside a single application module.

This allows us to demonstrate that `:sdk` behaves like a reusable SDK while `:app` acts as its consumer.

**This is our architectural decision; the assessment does not explicitly require two modules.**

### 2. Small public SDK API

The SDK exposes only:

- `Analytics.reportEvents(json, context)` – report events (the assessment's required function)
- `Analytics.observeQueueEvents(context)` – live queue for the Event Queue screen
- `Analytics.observeStatistics(context)` – live statistics for the Statistics screen
- `Analytics.retryPending(context)` – start a processing run now (Event Queue refresh button)

The application does **not** directly access:

- `EventProcessor`
- `EventDao`
- Room
- Deduplication
- `SessionManager`
- `InstallationManager`

These remain internal SDK implementation details.

**Reason:** The assessment explicitly asks for a function through which the application can report events. The other three functions give the screens read-only views of the data and a manual retry trigger, so the application still never touches Room, the DAO or the processor directly.

### 3. SDK owns IDs

The client does not generate or pass IDs.

The SDK manages:

- `sessionId`
- `installationId`

`installationId` is persisted so that the same application installation retains the same ID across app restarts.

### 4. `installationId` instead of `deviceId`

The original working notes used the term `deviceId`. We changed this to `installationId`, because our implementation identifies the **application installation**, rather than attempting to identify the physical device.

```
App installation
      ↓
installationId
```

The ID is generated by the SDK and persisted using `SharedPreferences`.

### 5. SDK-owned processing

The application does not implement ingestion or retry logic.

```
:app
   ↓
reportEvents()
   ↓
:sdk
   ↓
EventProcessor
   ↓
Room
```

This keeps event-processing responsibilities inside the SDK.

## Step 1 – Event Reporting

### Requirement

The application needs a function through which it can report multiple events.

### Implementation

The client calls:

```kotlin
Analytics.reportEvents(
    json = json,
    context = context
)
```

The SDK accepts JSON such as:

```json
{
    "events": [
        "INSTALL",
        "VISIT",
        "PURCHASE"
    ]
}
```

The SDK parses the JSON into an `EventRequest`.

### Responsibility

```
:app
  ↓
JSON
  ↓
Analytics.reportEvents()
  ↓
:sdk
```

The client does **not** manage:

- IDs
- timestamps
- deduplication
- Room
- retry
- processing status

### Invalid input

`reportEvents()` never crashes the application on bad input:

- Malformed JSON (for example `{ "events": [INSTALL }`): nothing is reported, the error is logged and the call returns.
- Unknown event type (for example `"LOGIN"`): that entry is skipped with a warning; the valid events in the same call are still reported.

Parsing errors are caught as `IllegalArgumentException`, which `SerializationException` extends. Event names are matched against `EventType.entries` instead of `EventType.valueOf()`, which throws.

### Change from original plan

**Added:**

- Explicit SDK boundary.
- JSON parsing inside SDK.
- `Analytics.reportEvents()` as the entry point for reporting events.
- Safe handling of malformed JSON and unknown event types.

**Removed:**

- Any need for the client to manage event-processing logic.

## Step 2 – Event Enrichment

When an event enters the SDK processing pipeline, the SDK adds:

- `timestamp`
- `sessionId`
- `installationId`

### Flow

```
Raw Event
   ↓
SDK
   ↓
+ timestamp
+ sessionId
+ installationId
   ↓
Enriched Event
```

Example:

```kotlin
Event(
    eventType = EventType.VISIT,
    timeStamp = System.currentTimeMillis(),
    sessionId = sessionId,
    installationId = installationId
)
```

### Session ID

`sessionId` is generated and managed by the SDK.

For the current implementation, the session represents the current application process/session.

### Installation ID

`installationId` is generated once and persisted using `SharedPreferences`.

```
First installation
      ↓
Generate UUID
      ↓
Persist installationId

App restart
      ↓
Read existing installationId
```

### Change from original plan

**Changed:** `deviceId` to `installationId`.

**Added:**

- Persistent installation ID management.
- SDK-owned ID generation.

## Step 3A – Deduplication

The SDK applies event-specific deduplication rules.

| Event | Rule |
|---|---|
| `INSTALL` | Process only once per installation |
| `VISIT` | Process only once per session |
| `ADD_TO_CART` | Process normally |
| `PURCHASE` | Process normally |

### Flow

```
Enriched Events
      ↓
Deduplication
      ↓
Valid Events
      ↓
Room Queue
```

### INSTALL

The SDK checks whether an `INSTALL` event already exists for the current `installationId`.

```
INSTALL
   ↓
Already exists for installation?
   ├── Yes → Skip
   └── No  → Queue
```

### VISIT

The SDK checks whether a `VISIT` event already exists for the current `sessionId`.

```
VISIT
   ↓
Already exists for session?
   ├── Yes → Skip
   └── No  → Queue
```

### Important implementation decision

Deduplication is performed **before inserting the event into the processing queue**.

Also, an existing event is considered for deduplication regardless of whether it is currently `PENDING`, `PROCESSING`, `FAILED` or `PROCESSED`.

This prevents duplicate events from being inserted while an earlier event is still being processed or retried.

### Concurrent reports

Every `reportEvents()` call runs in its own coroutine. Without protection, two calls made close together could both check for an existing `VISIT` in the same session, both find none, and both insert one.

The check and the insert therefore run under a single lock (`insertMutex` in `Analytics`). One call finishes checking and inserting before the next call starts checking, so the second call sees the first call's row and skips it as a duplicate.

Processing starts after the lock is released, so a slow retry never delays new events being recorded.

### Change from original plan

**Added:**

- Deduplication against events already present in Room.
- Deduplication before queue insertion.
- Installation-based `INSTALL` deduplication.
- Lock around check-and-insert so concurrent calls cannot create duplicates.

## Step 3B – Event Queue

Valid events are stored in Room as queue entries.

```
Valid Event
     ↓
Room
     ↓
PENDING
     ↓
Processing
```

The queue is persistent rather than an in-memory list.

### Event status

| Status | Meaning |
|---|---|
| `PENDING` | Event is waiting to be processed. |
| `PROCESSING` | Event is currently undergoing an ingestion attempt. |
| `FAILED` | The latest ingestion attempt failed and the event will be retried. |
| `PROCESSED` | The event was successfully ingested. |

### Change from original plan

**Added:**

- Explicit processing states.
- `PROCESSING` state.
- Retry count.
- Persistent queue entries in Room.

## Step 4 – Local Database for Ingestion Mocking

Room is used to simulate the ingestion pipeline.

```
Event
 ↓
Room
 ↓
EventProcessor
 ↓
Mock ingestion
```

Room has two important roles:

- Persistent event queue
- Persistent processed-event history

### Point 1 – Simulate Event Ingestion Using Room

Events are inserted into Room before processing.

```
Event
 ↓
Room
 ↓
EventProcessor
 ↓
Ingestion attempt
```

This means events do not exist only in memory. If the application closes:

```
App closes
    ↓
Room remains
    ↓
Events remain persisted
```

### Point 2 – Random Delay

Before every ingestion attempt, the SDK waits for a random duration between **1–5 seconds**.

Example:

```
Event 1 → 3 sec → ingestion
Event 2 → 1 sec → ingestion
Event 3 → 5 sec → ingestion
```

The delay is generated independently for every attempt. Therefore, **retries also receive a new random delay**.

### Point 3 – 20% Random Failure Rate

Every ingestion attempt has:

- 80% → Success
- 20% → Failure

```
Ingestion Attempt
       ↓
  Random Result
    ↙       ↘
  80%       20%
 Success    Failure
    ↓          ↓
PROCESSED    FAILED
               ↓
             Retry
```

This simulates temporary real-world ingestion failures.

### Point 4 – Retry Failed Events

Failed events remain in Room. They are **not deleted**.

```
FAILED
   ↓
Retry
   ↓
PROCESSING
   ↓
 ┌───────────────┐
 ↓               ↓
Success        Failure
 ↓               ↓
PROCESSED       FAILED
                 ↓
                Retry
```

The event continues retrying until the ingestion attempt succeeds.

There is currently **no retry limit**, because the assessment requires failed events to be retried until successfully processed.

#### Retry backoff

After a failure the SDK stores `retryCount` and `nextRetryAt` on the event. The wait before the next attempt doubles with each failure and is capped at 30 seconds:

| Failure | Wait |
|---|---|
| 1st | 2 s |
| 2nd | 4 s |
| 3rd | 8 s |
| 4th | 16 s |
| 5th onward | 30 s |

The Event Queue screen reads `nextRetryAt` and shows a live "Retrying in Ns" countdown.

#### Processing order

Events are processed one at a time, oldest first. A failed event is retried until it succeeds before the next event starts, so a failing event holds up the events behind it while it waits out its backoff.

Note: in the mock design, later events finish while an earlier one shows "Retrying in 2s". Our queue will not look like that. Changing it would mean moving on to the next event after a failure and coming back when `nextRetryAt` is due.

### Point 5 – Events Are Not Lost When App Closes

Because the queue is stored in Room:

```
App closes
    ↓
Events remain in Room
    ↓
App starts again
    ↓
SDK processing resumes
    ↓
Pending / failed events continue processing
```

This provides persistent event storage across application restarts.

Processing resumes automatically on app start through `AnalyticsInitializer` (androidx.startup). The Event Queue refresh button calls `Analytics.retryPending()` to start a processing run without restarting the app.

Processing runs only while the app process is alive. Only one processing run happens at a time (`EventProcessor` holds a lock), so the same event is never picked up twice.

### Change from original plan

**Added:**

- `PROCESSING` status.
- Persistent `FAILED` status.
- Retry count.
- Retry loop until success.
- SDK-owned event processor.
- Exponential backoff (2 s doubling, capped at 30 s) stored as `nextRetryAt`.
- Automatic resume on app start (androidx.startup).
- Manual processing run via the Event Queue refresh button.

## Step 5 – Persistence

Every successfully processed event remains stored in Room.

```
Event
 ↓
Queue
 ↓
Processing
 ↓
Success
 ↓
PROCESSED
 ↓
Remain in Room
```

The event is **not deleted after successful processing**.

This gives us a persistent processing history that can later be used by the Statistics screen.

### Example

`events` table:

| ID | Type | Status |
|---|---|---|
| 1 | INSTALL | PROCESSED |
| 2 | VISIT | PROCESSED |
| 3 | PURCHASE | PROCESSED |
| 4 | ADD_TO_CART | PROCESSED |

### Why this matters

The Statistics screen can calculate, from the persisted Room data:

- Successfully processed events
- Total processed events
- Total visits
- Event-wise statistics

### Change from original plan

**Clarified:** Room is not only the temporary queue. It also acts as the **persistent source of processed-event history**.

## Step 6 – Application Screens

The `:app` module has three screens, switched from the bottom navigation.

### Event Queue

- Lists events oldest first with a live status: Queued, Processing, Processed ✓ or Retrying in Ns.
- IN PROGRESS tab: events that have never failed.
- FAILED / RETRYING tab: events that are `FAILED` or have failed at least once (`retryCount > 0`).
- The retry countdown updates every second.
- Refresh icon: calls `Analytics.retryPending()`.

### Statistics

All numbers come from `PROCESSED` events through `Analytics.observeStatistics()` and update live. Nothing is hardcoded.

- Total Events Processed: number of `PROCESSED` events.
- Total Visits (Unique Session): number of distinct `sessionId`s among processed `VISIT` events.
- Event cards: processed count per event type.
- Event Breakdown: count and percentage of the total (2 decimals; 0.00% when nothing is processed yet).

### Mock Data

Builds an events JSON from buttons and sends it through `Analytics.reportEvents()`.

This screen stays in the submission: it is how the reviewer feeds events into the APK and tests the deduplication rules. The mock design shows only the two screens the assessment asks for.

### Change from original plan

**Added:**

- Statistics screen wired to live Room data.
- Refresh button starts a processing run.
- Mock Data screen as the input for the APK.
